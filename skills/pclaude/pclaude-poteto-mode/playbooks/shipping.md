### Shipping

**You own what lands. Verify each PR independently, land only the verified run from the root, then keep your hands off the stack.**

1. **Verify each PR independently before it lands.** Every PR operation goes through the GitHub CLI (`gh`). Never require Graphite (`gt`). Spawn one verifier per PR with the Agent tool: `subagent_type: "general-purpose"`, `isolation: "worktree"`, `run_in_background: true`, and the `judgment and prose` model from `../models.md` (`realpath ~/.claude/skills/pclaude-poteto-mode/../models.md` finds it). Use `isolation: "remote"` only when Billy asks for remote verifiers. Each verifier checks out the parent and the head in its own worktree and runs the change the way a user would, on its real surface: the `claude-in-chrome` skill for browser and web UIs, and the `run` skill or tmux for CLIs, TUIs and servers. Its prompt tells it to edit no code, post nothing to GitHub, and return `PASS`, `PASS+NOTES`, or `FAIL` with its evidence and the head SHA it verified. When a verifier returns, you post its verdict on that PR (step 7). Only a verdict from an agent that did not write the code counts, because an author checks what it meant to build. Green CI and an approving bot review are not verdicts, because neither runs the change as a user would.
2. **Land only the contiguous verified run rooted at the bottom.** Walk up from the lowest unmerged PR and stop at the first one without `PASS` or `PASS+NOTES`. The PRs below it are the run, and the top one is the ceiling. A verified PR above an unverified one waits, because it cannot land without the code below it. One whose branch neither holds nor needs that code can move onto trunk and land on its own. It needs a fresh verdict first, because its old one ran with that code beneath it and trunk does not have it.
3. **Re-check that the verdicts still describe the code.** A verdict covers a patch, and a chain rebase moves every PR above it to a new SHA without failing any check. Compare `git patch-id` at the verdict SHA with the current head before trusting an older verdict. When the patches differ only in tests, docs, or lint config, a lane's result stands if what it ran builds the same at both SHAs apart from noise. Noise is a difference that also shows up between two builds of the verdict SHA, or an embedded commit SHA. Report each kind of noise with its files, so a reader can check the call. The change itself still gets fresh checks and a review, because the old verdict never saw it. A lane with no build output, such as a dev server, cannot show this, so rerun it, and re-verify anything else that drifted.
4. **Land bottom-up, one PR at a time.** Always merge the run's lowest unmerged PR, with `gh pr merge <pr> --squash`. A PR whose base is still its parent's branch merges into that branch, not trunk. Read the PR back for the result (`gh pr view <pr> --json state,mergedAt,baseRefName`), because a merge command can report success when a merge queue only queued the PR, and a requested auto-merge is not a merge. A landed PR reads merged with trunk as its base, not its parent's branch. Arm `gh pr merge <pr> --squash --auto` only on a PR whose verdict covers its current head, because it lands whatever head is ready. After a merge lands, retarget the PR whose base was the merged branch to trunk (`gh pr edit <pr> --base <trunk>`), move its patch onto the merge result, and push with `--force-with-lease`. The verdict covers the patch, not its commits, so step 3's patch-id rule decides whether the verdict survives. Merge it once its checks pass and its verdict survives.
5. **Leave the stack alone while it lands.** Step 4's move of the next PR is the only change to a branch or base, because a merge lands whatever its branch and base hold at that moment, verdict or not. Watch the run with the queued watcher from `playbooks/babysit.md` (`scripts/watch-pr/watch-pr --queued-stack --stack-prs <bottom-to-top> --comments-since <cursor>`, with the last `commentsCursor` from Babysit) under `/loop` until it reports `COMPLETE` at the ceiling. A comment that lands mid-run stops the watcher with `BLOCKER: pr-comments` or `BLOCKER: review-threads`. Triage it per Babysit step 8 before anything else merges, because a human may be asking you to hold. A base that moves to trunk when its parent merges is expected, not damage to repair. If a merge stalls, find out why before you change anything.
6. **Stop at the ceiling.** Extending the run takes new verdicts, so it is a new pass through step 1.
7. **Post exactly this to GitHub, and nothing else.** Write every body to a file and pass the file. Every body starts with the line `<!-- pclaude -->`, so the watcher skips it.

   | What | Command | When |
   | --- | --- | --- |
   | A verifier's verdict | `gh pr comment <pr> --body-file <file>`, with `PASS`, `PASS+NOTES` or `FAIL`, the verified head SHA, and the evidence | When that PR's verifier returns |
   | A merge | `gh pr merge <pr> --squash` | Step 4, only after an explicit request to land or ship |
   | Auto-merge | `gh pr merge <pr> --squash --auto` | Step 4, only on a PR whose verdict covers its current head |
   | A retarget | `gh pr edit <pr> --base <trunk>` | Step 4, after the PR's parent merges |
   | The moved patch | `git push --force-with-lease` to that PR's branch | Step 4, right after the retarget |
   | Comment replies | per Babysit step 8 | When a comment arrives mid-run |

   Shipping never approves, closes, labels, or edits a PR's title or body.

**Reply:** the verified run and its ceiling, each PR's verdict and who produced it, what landed and how you confirmed it, and what the next gap needs.
